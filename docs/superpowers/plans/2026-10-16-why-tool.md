# `why` as an MCP tool (D169) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal, in the owner's words:** *"As an MCP tool, not only a CLI command: I want to explore the effort. I'm interested in building this."* (2026-10-16; added to v1 as D169, built after item 5.) An agent that reaches TaskFollow through its tools can answer "what happened, and why?" without running a shell command.

**Architecture:** One new `meta` tool, `why.show`, in the default tool set. It calls the existing `whyCommand` (`src/core/why.ts`) with the same argument the CLI takes and returns its JSON unchanged. Nothing else changes: no new storage, no new output, no change to `why` itself.

**Tech Stack:** TypeScript on Node 22, vitest; no new dependencies.

**Measured against:** D169, D138 (`why`), D146 (`why direct`), D164 (waiting "I noticed" suggestions), INSTALL.md operator rule 11. Nothing else is added.

## What exists

- `taskfollow why [<run id> | <date> | direct [<day>]]` (`cli.ts:425`): JSON for an agent (stdout not a TTY), plain lines for a person (`renderWhy`).
- TaskFollow's MCP server (`mcp-serve`, `mcp-server.ts`) lists the default tool set (`tool-set.ts:11`); Claude Code shows each as `mcp__installer__<group>_<action>` (`register.ts:53`, D56). `taskfollow tool <name>` runs the same tools from a shell.
- `meta` tools (`tools.ts:40`) are fixed L0, never gated, take no `approval_token` (`tools.ts:72`, `:104`), run while paused (`tools.ts:75`), and are never audited by the gate (L0 is silent, `tools.ts:53`). `check.ping` is the model (`check-tools.ts`).
- No workflow can use a `meta` tool: tool steps, approve steps, agent-step `tools` and context tools all go through `workflowTool`, which refuses it (`workflow.ts:161-165`).
- Tasks: every task run is given TaskFollow's MCP server (`agent-task.ts:105`), and TaskFollow's own code builds a task whose `may_use` names one of its tools (`check-runner.ts:62,104`: `mcp__installer__check_ping`). What keeps a task away from any other TaskFollow tool is (1) `--allowedTools`, which holds only the step's `may_use` plus the reason tool (`agent-task.ts:86`), and (2) the hook, which refuses any call that no `may_use` rule matches (`agent-hook.ts:89-96`, `matchesRule`), and in exact mode anything but the approved call (D151). A workflow author cannot add one: `may_use` refuses `mcp__installer*` (`workflow.ts:222`).

## The tool

| | |
|---|---|
| Name | `why.show` (Claude Code: `mcp__installer__why_show`) |
| Level | `meta`: fixed L0, no approval token, runs while paused, in sandbox too (it only reads) |
| Description (tools/list) | "What happened and why, from TaskFollow's own records: the runs since a date (default: the last 24 hours) with their results, one run's timeline (who did what, and why) by its id, or one day's direct calls to watched services. It changes nothing, except that waiting suggestions are shown only once: tell the person about them." |
| Input | `{ "run"?: string (maxLength 32), "since"?: string (maxLength 40), "direct"?: string (maxLength 10) }`, at most one of them; no other keys. `direct` is a day; for today the agent passes today's date (no boolean form) |
| Output | `whyCommand(home, arg, now, extra)` for the matching CLI argument (`run` → `why <run>`; `since` → `why <since>`; `direct` → `why direct <day>`; none → `why`), with `suggestions` and `suggestions_damaged` moved to the front of the object when present (below) |

**Mapping, checked per key in `parse`:** `whyCommand` decides the form from the value alone (`why.ts:150-156`), so a value in the wrong key would cross forms: `{"run":"2026-10-01"}` would run the list form and clear the suggestions, `{"since":"2026-10-14-1a2b3c4d"}` would look up a run, `{"run":"direct"}` would list direct calls. So `parse` checks `run` against `RUN_ID`, `since` against `DATE` and `direct` against `DAY`, exported from `why.ts`, and refuses a mismatch naming the key: "why.show: run must be a run id, for example 2026-10-14-1a2b3c4d", "why.show: since must be a date, for example 2026-10-13", "why.show: direct must be a day, for example 2026-10-14". The patterns also bound the length, matching the schema's `maxLength`.

**Output order.** The MCP server sends the result twice (text and `structuredContent`, `mcp-server.ts:60`) with no cap of its own. A client that cuts a long answer cuts from the end, so the tool puts `suggestions` and `suggestions_damaged` first: notices that were just cleared can never be the part that is cut. The builder checks a real client's limit on a large fixture (Task 1) instead of assuming it.

**What it never returns:** anything `taskfollow why` does not already return. `why` shows tools, the names of what they were given (`summarize`), the agent's stated reasons, approvals and run results cut to 300 characters; it never shows a secret, a token or a payload value beyond those (D138, D146). The tool adds no field.

### The one side effect: waiting suggestions (D164)

The list form (no argument, or `since`) calls `takeSuggestions`, which returns the waiting "I noticed" suggestions, clears them and audits `watch.noticed_shown` (`why.ts`, `watch-notice.ts:82-89`). **The tool keeps this, unchanged.** Why that is right, and not a read-only tool silently consuming notices:

1. The tool is `meta`, so no workflow step can call it, and no task can, because neither `--allowedTools` nor the hook lets a task reach a TaskFollow tool its `may_use` does not name (above; tested in Task 1). It runs only in a session the agent has with the person, which is exactly where operator rule 11 already runs `taskfollow why` today, non-TTY, getting the same JSON with the same clearing.
2. The description says so, and rule 11 says it: the agent tells the person each suggestion; each is shown once.
3. A version that did not clear would show the same suggestion every session to an agent without a shell (the reason for this tool), breaking D164's "once". A version with a "peek" flag is a new requirement.

The plan states this as the tool's behaviour and tests it (Task 1).

## What the person sees

Nothing new on screen. When they ask their agent "why did that happen?" or start a session, an agent without a shell now answers from TaskFollow's records instead of saying it cannot run commands. The words are the agent's; the facts are the same as `taskfollow why`.

## Human task

None. Claude Code's use of TaskFollow's MCP tools is already proven on the real agent (T5, task 34, D159), and the tool's output is `why`'s, tested above. If the owner wants to see it, it shows up in normal use after merge (ask the agent "what ran since yesterday?").

## Risks

1. **The refusal message for a workflow says "approval bookkeeping"** (`workflow.ts:164`), already inaccurate for `check.ping`. A workflow author naming `why.show` gets that wording. Left as is (out of scope); noted for a later wording pass.
2. **Import cycle.** `why.ts` imports `task-step.ts`; the lazy import in `run` avoids any cycle through `tool-set.ts`. Typecheck and the e2e `mcp-serve` test catch a mistake.
3. **Large answers.** A day with many runs returns a long JSON, sent twice by the server (`mcp-server.ts:60`), as the command's JSON is today; no new cap (the result field is already cut at 300 characters per run). Suggestions go first so a client's cut never hides them, and the builder checks a real client's limit (Task 1).

## Plan review applied (2026-10-16, Fable)

All eight findings accepted after checking the cited lines: per-key patterns against crossing forms (1, 7); the task guard is `--allowedTools` plus the hook, not a blanket rule, with two hook tests (2); suggestions first and a checked client limit (3); two e2e calls through the real server (4); deep-equal fixtures without suggestions (5); `direct` takes a day only, the agent passes today's date (6, the smaller choice); D169 says "read-only except D164's once-shown suggestions" (8).

## Out of scope

A text (rendered) form for the tool; a "peek" mode that keeps suggestions; any change to `why`'s content, its CLI, or the gate; exposing `why` to workflows or tasks.
