# Plan: WhatsApp minimum (connections design §5.5)

Status: revised after Fable's review (2026-10-15). Each slice test-first; fakes run as separate processes.

## Scope of v1
WhatsApp is **customer-facing**: customers message the business, workflows read those messages, a person approves the
exact reply on Telegram/Slack/terminal, and the reply is sent inside Meta's 24-hour window. Members do not join,
approve or pause over WhatsApp in v1 (their window is usually closed, which would stall approvals for everyone).
No templates.

## Relay (client's own free Cloudflare account; `relay/whatsapp-relay.mjs`, shipped and pinned by sha256)
- Secrets: `VERIFY_TOKEN`, `PULL_TOKEN`, `PATH_KEY` (random hex). Never the Meta token or app secret.
- `GET /webhook/<PATH_KEY>`: echoes `hub.challenge` as plain text when `hub.mode=subscribe` and the verify token
  matches; else 403. A wrong path is 404, so the callback address cannot be guessed from the script name.
- `POST /webhook/<PATH_KEY>`: stores the raw bytes (`arrayBuffer`, BLOB) and `X-Hub-Signature-256`; 413 over
  1.9 MB (D1 row cap 2 MB; such a batch is lost and the page says so); 503 when `max(id)-min(id)` reaches 5,000 rows
  or the stored bytes pass 50 MB (Meta retries later). It does not check signatures (no app secret).
- `GET /pull?after=<id>` with `Authorization: Bearer <PULL_TOKEN>` (constant-time compare): deletes `id <= after`;
  when it returned rows last time, also deletes rows older than 72 h (indexed `received_at`); returns up to 50 rows
  `id > after` as `{items:[{id, body_b64, signature, received_at}]}`. Anything else 404.
- Schema: `inbox(id integer primary key autoincrement, body blob not null, size integer not null, signature text not null,
  received_at integer not null)`, index on `received_at`.
- Tests run the real file under a Node shim (`Request`/`Response`, a D1 adapter over `node:sqlite`, `node:crypto` for
  the timing-safe compare).

## Assistant side
- **Signature first:** decode base64 → Buffer; HMAC-SHA256(app secret, bytes) vs the header without `sha256=`,
  timing-safe; only then `JSON.parse`. Mismatch → dropped, audit `channel.signature_rejected`. Then each
  `value.metadata.phone_number_id` must equal the stored one.
- **Messages:** `entry[].changes[].value.messages[]`; text keeps `text.body`; other types become a note ("(sent a
  photo: open WhatsApp to see it)"); `statuses` ignored. **Identity** = `from_user_id` when present, else `from`
  (Meta omits `from` for username users; the same person can change form after 30 days). `message_id` = `wamid` (Meta's
  retries collapse in the inbox). The envelope also keeps Meta's `timestamp` as `sent_at`.
- **Meta client** (Graph API v25.0, pinned): `GET /{phone_number_id}?fields=display_phone_number,verified_name`;
  `POST /{phone_number_id}/messages` `{messaging_product:"whatsapp", to | recipient, type:"text", text:{body,
  preview_url:false}}` (`recipient` for a username id `XX.digits`), body sliced to 4,096. Errors mapped to plain
  sentences (131047 → window closed); the token never appears in an error.
- **Window:** from the newest message of that address on WhatsApp, by Meta's `sent_at`. `channel.send` refuses
  (InputError, before any approval) when less than 10 minutes remain: "The customer last wrote at … ; WhatsApp only
  lets you reply within 24 hours. Ask them to write again, or use another channel." Checked again when sending
  (approvals live 24 h) → `channel.window_closed`. The approval announcement for a WhatsApp send says until when it
  can be sent.
- **Channel** `whatsapp`: `inbound: relay_poll`, `outbound_external: true`, `customers_only: true` (no join, no
  reply codes, no notify). Gateway pulls; when nothing waits, pulls again every 10 s until its wait ends.
  `waitsLong` includes `relay_poll`. `to` must be digits (8–15) or a username id.
- **Setup page** `taskfollow secret whatsapp`: (1) Cloudflare API token (Workers Scripts Edit, D1 Edit; account read):
  `GET /accounts`; reuse or `POST /d1/database {name:"taskfollow-whatsapp"}`; create table; `PUT
  /workers/scripts/taskfollow-whatsapp` multipart (`metadata`: `main_module`, `compatibility_date`, bindings
  `{type:"d1", name:"DB", database_id}` and three `secret_text`; module part `application/javascript+module`) — on a
  re-run with existing secrets in the keychain, `keep_bindings: ["secret_text"]` so the tokens Meta already has keep
  working; `GET /workers/subdomain` (PUT one when missing); `POST /scripts/…/subdomain {enabled:true}`. Shows the
  callback address and verify token to paste into Meta (subscribe `messages`). The Cloudflare token is not stored.
  (2) Meta System User token (not the 24-hour dashboard token), app secret, phone number id → checked with Meta.
  (3) "Send any WhatsApp message to your business number now" → pulls until one message passes the signature and
  phone-number checks → Connected. Keychain `whatsapp` = `{access_token, app_secret, pull_token}` (+ `verify_token`
  and `path_key` for re-runs); hand-off `whatsapp-settings` = `{relay_url, phone_number_id, display_number}`.
- `taskfollow channel whatsapp`, starter 1.7.0 (`services.whatsapp` + three steps), `taskfollow add whatsapp`; doctor
  pulls with the token (401 → "run secret whatsapp again"; repeated signature rejections → "the app secret changed");
  disconnect says the Worker stays in their Cloudflare account until they delete it.
- **Told to the person:** messages pass through Meta and Cloudflare and wait in their relay at most 72 hours.
